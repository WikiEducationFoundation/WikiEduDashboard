# Metrics glossary

The YAML files in this directory are the source for the public `/metrics`
page (`AboutThisSiteController#metrics`). Each entry defines one metric the
Dashboard computes, quotes the explanation the Dashboard gives for it, and
points at the code that calculates it. Places where the same name is
calculated in more than one way are recorded as *divergences*.

The glossary describes what the code does now, including its
inconsistencies. It's AI-drafted (the page says so) and checked against the
code by `spec/lib/metrics_glossary_spec.rb`.

## Files

- One file per family (section of the page): `contributions.yml`,
  `views_and_uploads.yml`, `participants.yml`, `breakdowns.yml`, ...
- `unclaimed.yml`: metric-like columns and translation keys without an
  entry, either `pending` (to be documented) or `ignored` (with a reason).
- `fingerprints.yml`: generated by `bin/rails metrics:accept`. Don't edit it.

## Family file format

```yaml
family:
  title: Edits and content      # section heading
  position: 1                   # order on the page
  intro: >-                     # optional Markdown

metrics:
  words_added:                  # page anchor: /metrics#words_added
    name: Words added
    summary: One sentence.
    definition: |               # Markdown; link other entries with (#key)
      ...
    audience: admin             # optional; hides the entry from non-admins
    deployments: [wiki_ed]      # optional; default is both (wiki_ed, pe)
    implementations:            # where it's calculated
      - ruby: WordCount.from_characters   # Class.method, Class#method or Class::CONST
        path: lib/word_count.rb           # needed for lib/ code, which isn't autoloaded
        formula: true                     # fingerprint this method (see below); constants always are
      - js: app/assets/javascripts/utils/wordcount_utils.js#bytesToWords
        note: Optional one-line note shown under the link.
      - file: app/views/term_recap_mailer/email.html.haml
    surfaces:                   # where people see it
      - i18n: metrics.word_count          # quoted on the page from en.yml
      - place: Course overview            # free text
    columns: [courses.character_sum]      # DB columns that store it
    related: [characters_added]           # other entry keys

divergences:
  words-rounding:               # page anchor; use hyphens to tell them apart from metrics
    title: Rounding of words added
    metrics: [words_added]      # entries it affects (any family)
    description: |              # Markdown
      ...
    code:                       # same format as implementations
      - ruby: WordCount.from_characters
        path: lib/word_count.rb
    status: undecided           # undecided | intentional | bug | fixed
    issue: 7303                 # optional GitHub issue number
```

Code pointers name symbols, not line numbers. The page looks up the line
when it renders and links to the commit that's deployed.

## The checks, and what to do when one fails

`bin/rails metrics:check` runs the same checks as the spec and prints every
problem.

1. **Well formed.** Required fields are present, there are no unknown
   fields, and cross-references between entries line up.
2. **References exist.** Every code pointer resolves, and every translation
   key and column exists. When you rename or delete something an entry
   points at, update the entry.
3. **Coverage.** Every metric-like database column (see
   `MetricsGlossary::Coverage`), every `metrics.*` translation key, and
   every `*_doc` translation key is claimed by an entry or listed in
   `unclaimed.yml`. When you add a stat column or tooltip, document it, or
   add it to `pending` (or `ignored` with a reason).
4. **Fingerprints.** The source of each `formula: true` method, and the
   value of each constant an entry points at, is recorded when someone has
   checked that the entries pointing at it still describe it. When you
   change one, the check fails until you re-read the entries it names,
   update them if the calculation changed, and run
   `bin/rails metrics:accept`. Mark only the method or two that define each
   number as formulas, so unrelated refactors don't trip this check.

   Only the marked method itself is fingerprinted, not the methods it
   calls, and JavaScript isn't fingerprinted at all. A change to a scope or
   helper that a formula relies on won't trip the check, so when you change
   code an entry points at, read the entry anyway.
